## Method

1. **Reconstruct**: `Session.create(id, events, header, 0, [imageOffloadProjection])` is the baseline rebuild used to validate the parser (1531/1531 events, final surface = 29 occurrences). The incremental replay appends the same events one at a time through `SessionPlayer`, rewriting `surfaceOp` replace windows and `sourceEventSeqs` from original seq → replay seq; a fresh session is used per pass.
2. **Isolate the cache**: the real `LocalAttachmentStore` is rooted at a temporary harness home with `attachments/v1` symlinked to `~/.dsh/attachments/v1` and an empty `cache/`. Request-version encoding therefore reads the real images and writes only below the temp home. `~/.dsh/cache` is untouched (temp home /tmp/ibg-replay-es6FXU; attachments/v1 → /home/ksndjaks/.dsh/attachments/v1; cache under /tmp/ibg-replay-es6FXU/cache).
3. **Measure**: `llm.imageRequestTarget(provider, model, ref)` → `attachments.readImageRequest(ref, target)` → `base64Length(version.bytes)`, summed over retained occurrences. That is the same byte accounting the inline route uses. `requiredImageOffload(deriveMessages(), {representation: "base64", maxBytes: ceiling})` is the real adapter-side predicate; `> 0` means the adapter would throw `IMAGE_OFFLOAD_REQUIRED`.
4. **Run the guard** (not a dry run) at every `step/start` boundary, then measure again. "Before" is the surface with all earlier decisions applied; the separate baseline pass has no guard at all.

**Adapter note.** The replay mounts a real `LlmRuntime` (the same dispatch path `runGuard` calls through) with a minimal `LlmAdapter` subclass instead of the full `PiAiAdapter`. The real pi-ai adapter derives its target from a settings/credentials-backed profile snapshot, while for this replay only two adapter-owned numbers matter; the subclass returns exactly `requestImageDimensions(w, h, pixelBudget)` + `maxBytes`, the expression `PiAiAdapter.imageRequestTarget` uses (`dsh-llm-pi-ai/lib/index.js:1379-1384`, `:1837-1845`). Model capability (text+image) and route metadata come from the same stored profile. No request is dispatched.

## Anomalies and caveats

- **Original log retries are not image-related.** All 19 `llm/retry` events split as 8 TRANSPORT + 11 SERVER — none is `IMAGE_OFFLOAD_REQUIRED`. The historical session never failed on image bytes, which is consistent with the mitigated policy keeping its peak (5.98 MiB) below the 6 MiB line.
- **Projected `IMAGE_OFFLOAD_REQUIRED`:** A · mitigated 0, B · unmitigated 0, C · unmitigated, tuned floor (retainSteps 0 / minRetainImages 6) 0, C2 · floor sweep (retainSteps 4 / minRetainImages 4) 0 (0 total) over all guarded steps. The guard keeps the adapter from ever rejecting a request in every pass.
- **Scenario C's pass is session-specific, not a universal guarantee.** The plugin budget counts **base64** bytes, so the protected 6-image floor fits 6 MiB only while those six request versions average ≈≤786 KB encoded each. The unmitigated per-image target allows 1 MiB **raw** (≈1.33 MiB base64), so six maximal images alone would be ≈8.0 MiB and the budget would again be unreachable without also lowering `minRetainImages`. This session's newest six average well below the cap, which is why C measures 5.96 MiB with only 37072 B of headroom.
- **Measurement is offline and encoding is deterministic**: no HTTP request is built; the payload is the exact base64 length of the request-version bytes the route would send.
- **Image-count cross-check:** 0 steps showed a difference between derived-message image blocks and the guard's eligible occurrence reader (expected 0; both count the same surface).
- **Guard failure reasons** (`estimate-failed`, `stale-surface`, `append-failed`, …): 0 steps.
